System Design Interview Framework

For AI Engineer / Python Backend roles · 15–20 LPA target · 2.5 YOE

Mental Trigger — Say This Out Loud First
Clarify → Scope → HLD → LLD → Scale → Trade-offs
1
Clarify Requirements
3–4 min
Never draw anything until you've asked these. Jumping straight to design = instant red flag.
Functional — what are we building?
What are the 2–3 core features? (skip nice-to-have)
Who are the users? (consumer, B2B, internal?)
What does the primary user flow look like end to end?
Are we building for read, write, or both? (read-heavy changes everything)
Non-functional — constraints
Scale: DAU? requests/sec? data stored?
Latency: real-time (<100ms), near-real-time (<1s), or batch (minutes)?
Availability: 99.9% (8hr downtime/yr) or 99.99% (52min/yr)?
Consistency: strong (banking) or eventual (social feed) is acceptable?
Geography: single region or global?
2
Scope + Estimates
2–3 min
Say what you will and won't cover. Interviewers want to see you make deliberate choices.
Say: "I'll design X. I'll skip auth, billing, and notifications — I'll call those external."
RPS: DAU × requests/user ÷ 86400 = RPS. Say the number out loud.
Storage: record size × daily writes × retention years = total GB/TB.
Read/write ratio: "This is 95% read, 5% write — I'll optimize for reads."
Confirm: "Does this scope work for you before I start the diagram?"
3
High Level Design (HLD)
6–8 min
Draw boxes and arrows. Keep it to 5–7 components. Talk while you draw.
Standard HLD components — include what applies
Client — web / mobile / API consumer
CDN — if serving static assets or globally cached data
API Gateway / Load Balancer — single entry point, routing, auth
Core Service(s) — main business logic (stateless)
Database — primary storage (SQL or NoSQL, justify)
Cache — Redis if read-heavy or session data
Message Queue — Kafka/SQS if async processing needed
Worker/Consumer — if queue exists, show who processes it
Object Storage — S3 if files, images, blobs

Talk-track while drawing
Where does data enter the system?
Where does it get stored?
Where does processing happen?
Where does the response go back to the user?
HLD Draw this on whiteboard / paper
4
Low Level Design (LLD) — Pick 2 Components
8–10 min
Pick the hardest/most unique parts. Don't try to deep-dive everything — you'll run out of time.
How to pick which components to LLD
What is the most complex part? (unique to this problem, not generic CRUD)
What is the biggest bottleneck at scale?
What would an interviewer expect you to know for this role?
Data model — draw the schema
Table/Document names and their key columns
Relationships: 1:1, 1:N, N:M — draw the FK arrows
Indexes: which columns get indexed and why
Partitioning/sharding key if at scale
// Example schema sketch (URL shortener)
urls { id, short_code (PK+idx), long_url, user_id, created_at, expires_at }
users { id, email (unique), created_at }
clicks { id, url_id (FK), timestamp, ip, country } ← partitioned by url_id
API design — state the contract
Endpoint: POST /v1/urls → { short_code, expires_in }
Response: 201 { short_url, expires_at } | 400 | 409 (conflict)
Auth: Bearer token / API key in header?
Pagination: cursor-based (preferred) or offset for large collections
Component internals — the actual algorithm/flow
What does the algorithm/logic look like step by step?
What happens on failure? (retry, fallback, circuit breaker, dead letter queue)
How is consistency maintained? (transaction, idempotency key, lock)
How do you handle concurrent writes? (optimistic lock, CAS, queue)
LLD Schema API
5
Scale — What Breaks at 10x?
3–4 min
This is where seniors separate from juniors. Don't just say "add more servers" — name exactly what breaks and why.
Work through the stack from top to bottom
Client: CDN for static assets, edge caching for popular data
API tier: stateless services → horizontal scale behind load balancer
Cache: Redis cluster, cache-aside pattern, TTL strategy, invalidation
DB reads: read replicas, connection pooling, query optimization
DB writes: sharding (name the shard key), CQRS, write-behind cache
Hot spots: consistent hashing to spread load, celebrity problem in social graphs
Async: move non-critical writes to queue (Kafka), batch processing
Global: multi-region, eventual consistency, data residency tradeoffs
6
Trade-offs — Defend Your Choices
2–3 min
Use the format: "I chose X because Y, the trade-off is Z, and I'd revisit this if W changes."
Standard trade-off decisions you'll always be asked
SQL vs NoSQL: SQL = ACID + relations + schema, NoSQL = flexible schema + horizontal write scale
Sync vs Async: sync = simpler + consistent, async = resilient + decoupled + higher throughput
Monolith vs Microservices: monolith = simple + fast iteration, micro = independent scale + deploy
Consistency vs Availability (CAP): name which side you picked and why
Strong vs Eventual consistency: banking = strong, social feed = eventual is fine
Push vs Pull: push = low latency, pull = server controls load
⚡ Cross-Questions — They Will Ask These
Multi-Tenancy
How do you isolate tenant data? → institute_id on every row, from JWT not client, 4-layer defense
Why not Postgres RLS? → adds session-variable complexity with async ORMs; service layer is sufficient at this scale
Database
What if your DB becomes the bottleneck? → read replicas first, then caching, then sharding last
What's your shard key? → high cardinality, even distribution, avoid joins across shards
How do you handle schema migrations at scale? → expand-contract pattern: add nullable column, backfill, switch reads, drop old
Caching
What's your cache invalidation strategy? → TTL + event-driven invalidation on write; write-through for critical data
What if cache fails? → thundering herd: use cache locks + probabilistic early expiry
Reliability
What happens if Service A fails mid-request? → idempotency key, retry with backoff, dead letter queue for async
How do you handle duplicate messages from Kafka? → idempotency key per message, dedup at consumer with Redis SET NX
Rate Limiting
How would you rate limit this API? → token bucket (smooth bursts) or sliding window (exact count). Redis ZADD or atomic counter
Per-user or per-IP? → per-user for authenticated, per-IP for public. Combine for public+auth APIs
For AI/RAG Systems Specifically
How do you prevent hallucination? → retrieval grounding: only facts from retrieved context; reject if retrieval score below threshold
How do you evaluate RAG quality? → retrieval: precision@k, recall. Generation: LLM-as-judge, RAGAS, faithfulness score
What if retrieval returns wrong chunks? → re-ranker (cross-encoder), hybrid search (dense + BM25), query rewriting
How do you scale vector search? → HNSW index (approximate), sharding by tenant/domain, incremental index update
How do you handle context window limits? → retrieve top-k, summarize if too long, MapReduce for long docs

⚡ Golden Rules

1. Clarify before drawing. Every time. No exceptions.
2. Say "I chose X because Y, trade-off is Z" — not just "I'd use Redis."
3. Think out loud. The interviewer wants your reasoning more than the answer.
4. You don't need a perfect design. You need a defensible one.
5. If stuck, go back to requirements. The answer is usually hidden there.
6. Name numbers. "About 1000 RPS" sounds 10× more credible than "high traffic."
7. For AI questions: lead with your ARIA experience. It's real production work, not toy demos.
VidyaTrack + ARIA = your two real examples. Anchor every answer in one of them.
