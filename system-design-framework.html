System Design Interview Framework

Based on Hello Interview Delivery Framework · For AI Engineer / Backend roles · 2.5 YOE

Interview Phase Map — Total ~38 minutes
① Requirements 5m → ② Core Entities 2m → ③ API Design 5m → ④ Data Flow 5m (pipelines only) → ⑤ HLD 12m → ⑥ Deep Dives 10m
The easiest way to fail is to never deliver a working system. Structure keeps you from getting stuck and ensures you finish. — Hello Interview
1
Requirements
~5 minutes
1A — Functional Requirements
→
These are "Users / Clients should be able to…" statements — the core features of the system.
→
This is a back-and-forth with the interviewer. Ask targeted questions like a PM: "Does the system need to do X?", "What would happen if Y?"
→
Maximum 3. Many of these systems have hundreds of features — your job is to identify and prioritize the top 3. A long list hurts more than it helps. Many top FAANGs directly evaluate your ability to focus on what matters.
▶ Say
"I see three core things users need here — [FR1], [FR2], [FR3]. Does that capture the main use cases, or is there something you'd prioritize differently?"
Always end with a verification question. It turns a recitation into a conversation and gives the interviewer a natural opening to redirect you before you build the wrong thing.
1B — Non-Functional Requirements
→
NFR = Non-Functional Requirements. These answer how the system behaves, not what it does. FR = "users can post a tweet." NFR = "the feed loads in under 200ms." Same system, different axis.
→
Phrased as "The system should be able to…" or "The system should be…" statements.
→
Pick top 3–5 that are most relevant to this specific system. Do not list all eight just to show you know them.
✗ Meaningless
"The system should be low latency." — obvious, not useful, nearly all systems should be.
✓ Useful
"The system should have low latency search, <500ms" — identifies the specific path and gives a target.
NFR Checklist — pick your top 3–5 for this system
1. CAP Theorem Core — always state
Should your system prioritize consistency or availability? Note: partition tolerance is a given in distributed systems. AP = stale data acceptable. CP = may be unavailable during partition.
e.g. "I'd prioritize availability over consistency — a slightly stale redirect is far better than the service being down."
2. Scalability Core — always state
All systems need to scale, but does this one have unique requirements? Bursty traffic at specific times? Events like holidays? Also consider the read vs write ratio — which must scale more?
e.g. "The scale here is roughly 833 reads for every 1 write — every design decision must optimize for reads."
3. Latency Core — always state
How quickly does the system need to respond? Specifically consider requests that require meaningful computation. Name the specific path and the target in milliseconds.
e.g. "Redirect latency needs to be under 50ms — this is the hot path at 10K RPS and every millisecond is felt by every user."
4. Durability Situational
How important is it that data is not lost? A social network might tolerate some data loss, but a banking system or URL mapping service cannot.
e.g. "Losing a URL mapping permanently breaks a link — durability is non-negotiable here."
5. Environment Constraints Situational
Any constraints on the environment? Running on a mobile device with limited battery? Limited memory or bandwidth (e.g. streaming video on 3G)? On-device vs cloud inference?
e.g. "The client SDK runs on mobile — we need to batch errors to avoid draining battery with per-event HTTP calls."
6. Security Situational
How secure does the system need to be? Consider data protection, access control, and compliance with regulations (HIPAA, GDPR, SOC2).
e.g. "Multi-tenant isolation is a hard requirement — one tenant's data must never appear in another's results."
7. Fault Tolerance Situational
How well does the system need to handle failures? Consider redundancy, failover, and recovery mechanisms.
e.g. "The scheduler is a single point of failure — it needs leader election or active-passive failover."
8. Compliance Situational
Are there legal or regulatory requirements? Industry standards, data protection laws, data residency requirements?
e.g. "Healthcare data — HIPAA compliance means all PII must be encrypted at rest and we need a full audit trail."
▶ Say
"For non-functional requirements I'm thinking: [NFR1 + specific number or reason], [NFR2 + specific number], [NFR3 + specific number]. Any specific constraints I should factor into my design?"
1C — Capacity Estimation (skip in most interviews)
✗
Many candidates calculate DAU, storage, and QPS only to conclude "ok, so it's a lot — got it." As interviewers, we gain nothing from this except that you can do basic arithmetic. — Hello Interview
✓
Only do the math when the number directly changes your design. Example: TopK system — you need to know if data fits in one min-heap or needs sharding. That is a number that changes the architecture.
▶ Say instead
"I'd like to skip upfront estimation and do the math if a specific calculation would directly change a design decision. Is that okay?"
2
Core Entities
~2 minutes
→
Identify and list the core entities of your system. This defines terms, helps you understand the central data, and gives a foundation to build on.
→
These are the core entities that your API will exchange and that your system will persist in a data model.
→
In the actual interview, this is as simple as jotting down a bulleted list and saying "this is my first draft."
Two questions to identify entities
1
Who are the actors in the system? Are any overlapping? (User, Admin, Worker, Service)
2
What are the nouns or resources necessary to satisfy the functional requirements? User posts tweet → Tweet. User follows user → Follow. User shortens URL → ShortURL.
▶ Say
"Before I draw anything, let me get the core data entities on the board — [Entity 1: one-line role], [Entity 2: one-line role], [Entity 3: one-line role]. I'll keep the schema intentionally light here and add the relevant columns next to the database as we go through each endpoint."
✗ Do Not
Write full table schemas with every column here. The interviewer knows a User table has name, email, and password hash — writing those wastes time and signals you don't know what to prioritize. Schema columns get added during HLD, placed directly next to the relevant database component in the diagram. Aim to choose good names for entities — some interviewers evaluate this as a design signal.
3
API or System Interface
~5 minutes
→
Define the contract between your system and its users before drawing anything. This guides the HLD — you build the architecture to satisfy this contract.
→
Your endpoints should map directly to the functional requirements you identified. One FR = one or two endpoints.
Protocol choice — decide first, state your reason
REST ← default
HTTP verbs (GET, POST, PUT, DELETE) on plural resource names. Use for any client-facing API with CRUD operations on named resources. Resources should be plural nouns.
Choose when: standard client-facing product, clear resource model, all clients need the same data shape.
GraphQL
Clients specify exactly what data they want. Avoids over-fetching and under-fetching.
Choose when: diverse clients with different data needs (mobile vs web), complex nested data requirements.
gRPC / RPC
Action-oriented, binary protocol, strongly typed. Faster than REST for service-to-service.
Choose when: internal service-to-service communication where performance is critical (e.g. rate limit check in the request path).
WebSocket / SSE
WebSocket = bidirectional persistent connection. SSE = server-to-client one-directional stream.
Choose WebSocket when: real-time bidirectional (chat, live games). Choose SSE when: server streams to client only (LLM token streaming, agent reasoning). Design core REST API first, add WebSocket/SSE on top for real-time features.
Endpoint format — REST example
// Use plural resource names. Current user from auth token — never from request body.

POST /v1/tweets
body: { "text": string }
→ 201: { "tweet_id": string, "created_at": timestamp }

GET /v1/tweets/{tweetId} → Tweet

POST /v1/follows
body: { "followee_id": string }
→ 201: { "follow_id": string }

GET /v1/feed?cursor=<cursor>&limit=20
→ 200: { "posts": Tweet[], "next_cursor": string }
✗ Security Rule
Never rely on sensitive information like user IDs from request bodies or path parameters when they should come from authentication. Always derive the current user from the auth token in the request header, not from user input.
4
Data Flow (Optional — pipeline systems only)
~5 minutes
→
For some backend systems — especially data-processing pipelines — describe the high-level sequence of operations the system performs on the inputs to produce outputs. Skip this for product-style interviews.
→
Define via a simple numbered list. You'll use this flow to inform your HLD — every box in the diagram represents a step in this list.
When to use it
✓
Use for: RAG pipeline, ETL pipeline, document processing, web crawler, ML training pipeline, event processing system.
✗
Skip for: URL shortener, chat system, news feed, rate limiter, file upload — these don't have a long sequence of transformations.
▶ Say
"Before I draw the architecture, let me walk through what happens to [a document / a data record / a user query] from the moment it enters the system to when it produces the output."
// Example: Web crawler data flow
1. Fetch seed URLs
2. Parse HTML
3. Extract URLs
4. Store data
5. Repeat

// Example: RAG pipeline query flow
1. User sends natural language query
2. Embed query using embedding model
3. ANN search in vector DB, pre-filtered by tenant_id
4. Top-k chunks retrieved and re-ranked
5. Chunks injected into LLM prompt
6. LLM generates grounded answer with citations
5
High Level Design
~10–15 minutes
→
Draw boxes and arrows representing components and how they interact. Your primary goal is to design an architecture that satisfies the API you defined and thus the requirements you identified.
How to build the diagram — most important guidance
1
Go one endpoint at a time. Take your first endpoint. Draw only the components it needs. Then move to the second endpoint and add components. Build up to the final diagram incrementally.
2
Talk while you draw. The interviewer needs to follow your reasoning, not just see boxes appearing. Be explicit about how data flows through the system and what state changes with each request.
3
Add schema columns next to the database in the diagram — not in a separate table. Only write columns that are specifically relevant to your design. Don't write name, email, password hash — the interviewer knows those.
4
When you spot complexity, name it and move on. Say: "I can see we'll want a cache here — I'm noting that for deep dives." Don't solve deep dive problems during HLD.
5
Finish only when all three FRs have a working data path. Don't move to deep dives until the basic system works end-to-end for all requirements.
✗ Most Common Mistake
Candidates start layering complexity too early — adding caches, queues, and sharding before the basic design is complete. This results in never delivering a working system. Focus on a simple design that meets the core functional requirements, then add complexity in Deep Dives to satisfy the NFRs.
Standard HLD components — include what this system needs
●
Client — web / mobile / API consumer
●
CDN — if serving static assets or globally cached hot data (e.g. popular URL redirects)
●
API Gateway / Load Balancer — single entry point, routing, rate limiting, auth, SSL termination
●
Core Service(s) — main business logic, stateless for horizontal scale
●
Database — primary storage (justify SQL vs NoSQL)
●
Cache — Redis/Memcached if read-heavy or session data
●
Message Queue — Kafka/SQS if async processing or fan-out needed
●
Worker / Consumer — if queue exists, show who processes it
●
Object Storage — S3 if files, images, blobs, or large binary data

Client ──→ [CDN] ──→ API Gateway ──→ Service A ──→ DB
                                                       ↕ Cache
                            Service B ←── Queue ←── Service A
6
Deep Dives
~10 minutes
→
Now that you have a working system, harden it by going back to the NFRs you stated in Phase 1 and addressing them one by one.
→
Also: address edge cases, identify bottlenecks, and improve the design based on probes from the interviewer.
▶ Transition — say this to start Deep Dives
"I now have a working system that satisfies all three functional requirements. Let me now harden it by addressing the non-functional requirements I identified at the start."
NFR-driven deep dive format — for each NFR
1
State the problem it creates in the current design: "The current design hits the DB on every redirect. At 10K RPS that's not sustainable — we won't hit the 50ms target."
2
Propose your solution: "I'd add Redis in front of the DB. Alias → original_url with a TTL. Cache hit rate for popular links is very high, so most redirects never touch the DB."
3
Pause. Let the interviewer probe. Don't monologue for more than 2 minutes. They have specific signals they want — if you're talking, they can't ask for them.
4
Move to the next NFR: "Let me now address [next NFR]…"
Stack-level breakdown — what typically breaks and how to fix it
●
Latency NFR: Add Redis cache → CDN at the edge → reduce DB round trips → connection pooling
●
Scale NFR (reads): Read replicas → cache cluster → horizontal scale of stateless services
●
Scale NFR (writes): Sharding (name the shard key) → CQRS → write-behind cache → Kafka for async
●
Availability NFR: Multi-AZ DB → replica failover → health checks → circuit breakers
●
Durability NFR: Synchronous replication to ≥ 2 replicas before ACK → regular backups → WAL
●
Hotspot / celebrity problem: Consistent hashing → local in-memory cache → CDN for read hotspots
●
Fault tolerance: Idempotency keys → retry with backoff → dead-letter queue for async → graceful degradation
Seniority signal: Junior candidates expect the interviewer to point out issues. Senior candidates proactively identify the next bottleneck and lead the discussion. But always balance talking with listening — give the interviewer room to ask questions and probe your design. They have specific signals they need to get, and you'll miss it if you're monologuing.
⚡ Cross-Questions — They Will Ask These
Database Choice
Why SQL vs NoSQL? → SQL = ACID + relations + fixed schema. NoSQL = flexible schema + horizontal write scale. Name the specific tradeoff for this system.
What if your DB becomes the bottleneck? → read replicas first, then caching, then sharding last — in that order
What's your shard key? → high cardinality, even distribution, avoid joins across shards (e.g. user_id for user data, alias for URLs)
Schema migrations at scale? → expand-contract: add nullable column, backfill, switch reads, drop old column. Never rename in place.
Caching
Cache invalidation strategy? → TTL + event-driven invalidation on write. Write-through for critical data. Write-behind for high-throughput.
What if cache fails / thundering herd? → cache lock (mutex) + probabilistic early expiry. Or staggered TTLs.
Cache-aside vs write-through? → cache-aside = lazy loading (simpler, can have cache miss on first request). Write-through = always warm (adds write latency).
Reliability
What if a service fails mid-request? → idempotency key, retry with exponential backoff, dead-letter queue for async, circuit breaker for downstream
Duplicate messages from Kafka? → idempotency key per message, dedup at consumer with Redis SET NX or DB upsert on unique key
At-least-once vs exactly-once? → at-least-once is sufficient if your handlers are idempotent. Exactly-once is very expensive — usually not worth it.
API Design Probes
Pagination strategy? → cursor-based (preferred for large datasets, no skipped rows) vs offset (simple but breaks on inserts). Always cursor for feeds.
API versioning? → URL versioning (/v1/, /v2/) is simplest. Header versioning is cleaner but harder to test. Never break existing clients.
Rate limiting this API? → token bucket (smooths bursts) or sliding window (exact count). Redis atomic counter or ZADD sorted set. Per-user for auth, per-IP for public.
Consistency & Trade-offs
Consistency vs Availability? → name which side you chose and why. "AP — a stale result is better than downtime." or "CP — data loss is unacceptable here."
Sync vs async? → sync = simpler + consistent. Async = resilient + decoupled + higher throughput. Move non-critical writes to queue.
Push vs pull for fan-out? → push (fan-out on write) = low read latency, expensive for celebrities. Pull (fan-out on read) = always fresh, slow for large follow graphs.
For AI / RAG Systems
How do you prevent hallucination? → retrieval grounding: only use facts from retrieved context. Reject if retrieval score below threshold. Citation in response.
How do you evaluate RAG quality? → retrieval: precision@k, recall@k, MRR. Generation: faithfulness, RAGAS, LLM-as-judge.
Wrong chunks retrieved? → re-ranker (cross-encoder), hybrid search (dense + BM25), query rewriting, parent-child chunking
Scale vector search? → HNSW index (approximate), pre-filter by tenant_id before ANN, sharding by tenant/domain, incremental index update
Context window limit? → retrieve top-k, summarize if too long, MapReduce for very long docs, sliding window memory for chat
Multi-tenant isolation? → pre-filter by tenant_id in vector search (never post-filter). Separate index per tenant for largest tenants.
🤖 AI System HLD Template (RAG / Agent / LLM Chatbot)
Standard AI/RAG pipeline components
●
Ingestion Pipeline: Doc loader → Chunker (512 tokens, 50 overlap) → Embedder → Vector Store + metadata DB
●
Query Pipeline: User query → Embed query → Pre-filter by tenant → ANN search → Re-rank → Pack context → LLM → Response
●
Vector Store: Qdrant / Weaviate / pgvector — HNSW index for approximate nearest neighbor
●
LLM Gateway: Rate limiting, cost tracking, model routing (LiteLLM), fallback, prompt caching
●
Guardrails: Input validation, output validation, topic scoping, HITL approval for writes
●
Eval Layer: Retrieval metrics (precision@k, recall@k, MRR), generation metrics (faithfulness, RAGAS)
●
Semantic Cache: Embed query → cosine similarity lookup → return cached answer if score > 0.95

⚡ Golden Rules

1.Clarify before drawing — always. Never jump to design before understanding the problem.
2.State 3 FRs maximum. A long list hurts more than it helps. FAANG directly evaluates your ability to focus.
3.Always quantify NFRs. "The system should be fast" means nothing. "Redirect latency under 50ms on the 10K RPS read path" shows you understand the system.
4.Skip capacity estimation unless the number changes your design. Say: "I'll skip estimation upfront and do the math if a calculation would change a design decision."
5.Build HLD one endpoint at a time. Talk while you draw. Note complexity and move on — don't solve deep dive problems during HLD.
6.Deep dives are NFR-driven. Lead with: "Let me now address the non-functional requirements I identified." Go through them one by one, state problem → solution, then pause.
7.Say "I chose X because Y — the trade-off is Z." Not just "I'd use Redis."
8.Think out loud. The interviewer wants your reasoning more than the final answer.
9.If you get stuck, go back to requirements. The answer is usually hidden there.
10.Give the interviewer room to probe. If you're monologuing, they can't get the signals they need.
